1. A visitor follows the default installation path to an existing qualified artifact, verifies its checksum, and runs the disclosed account-free repository walkthrough. Development-only instructions do not advertise unpublished assets as available downloads.
2. An owner can submit through the supported installed OpenClaw tools, observe the same durable Keep job/proposal, and obtain one genuinely generated proposal checked against predefined tests. The direct CLI remains usable. OpenClaw gets bounded submission/status authority, not the owner's approval credential or Codex auth cache. Use the already frozen public task/checker where applicable. Preserve the original failed first attempt. No separate API key or invented dollar price is required.
3. The installed profile demonstrates useful permitted work and concrete refusals: no generation before exact approval, wrong decision/token/proposal refusal, source preservation before a bound action/veto, restart without automatic replay, and required-jail useful work plus denial/refusal. Inspect actual files, calls and persisted outcomes; printed success alone is insufficient.
4. A short engineering walkthrough explains the trust boundaries, a verified defect/fix, tradeoffs and residual risks, with commands and links to actual evidence. It distinguishes controlled fixtures from genuine generation, and secure design from production enterprise qualification.
5. One final exact-source package passes the existing required qualification and clean-consumer checks. Download, source/version, commands, checksums and public evidence agree. Previously recorded results keep their original identities.
6. The selected OpenClaw profile can perform the allowed request/status workflow while refusing self-approval, unrelated-job access, duplicate dispatch and direct repository-write bypass through its exposed tools. Keep unavailability causes a hold/error, not unrestricted fallback. Qualify in an owned disposable instance; no running Effie, Plutarch or other claw is modified. A trusted OpenClaw host/plugin is still part of the threat model; a plugin hook alone is not a hostile-host boundary.
7. Required supporting behavior is explicit: usable no-generation readiness, current dependency/advisory/public-content admission, component-complete protected backup/upgrade compatibility, and interruption of one owned job without disrupting another. These are necessary inferred release work, not new broad feature families. Privacy/consent, authority and uncertainty restrictions apply across the workflow.
